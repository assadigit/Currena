    50→    50→## 4. Building
    51→    51→
    52→    52→- **Milestones and sub-milestones.** After each verified sub-milestone: commit with a clear message, then push. If the session dies, nothing is lost. Every commit must leave the project in a working state.
    53→    53→- **Small verified steps.** Change, check, then continue. Do not pile up unverified edits.
    54→    54→- **Stay in scope.** Make the smallest change that fully solves the request. Report unrelated problems instead of fixing them. No drive-by refactors, mass renames or surprise dependency upgrades.
    55→    55→- **No giant files ("god-modules").** One file, one responsibility. Roughly: over ~400 lines, consider splitting; over ~800 lines, split or justify in `DECISIONS.md`. Put new code in a new, well-named module instead of enlarging an oversized file. Group files in sensible folders.

    57→    57→- **Never invent** functions, packages, flags, file paths or results. Check they exist in the installed version.
    58→    58→- **Never weaken tests, linters or checks to get green.** Fix the cause. If a check is genuinely wrong, explain and ask.
    59→    59→- **Debugging:** reproduce first, find the root cause, fix it, add a regression check. After about 3 failed attempts at the same approach, stop, change strategy or ask. Never loop endlessly and never work around a permission block.

    68→    68→**Stop and ask first. Standing approval does NOT cover:**
    69→    69→- force-pushing, rewriting published git history, skipping hooks;
    70→    70→- deleting or overwriting data or files you did not create (database rows or tables, KV keys, uploads, the owner's files);
    71→    71→- anything that reaches real customers or money: sending emails/messages, charging or refunding, changing prices, editing live orders;
    72→    72→- changing DNS, domains, permissions, billing, or access for other people;
    73→    73→- using real production data for testing or experiments;
    74→    74→- any action that cannot be undone and is not covered by a verified backup.
    75→    75→

   228→   228→## 13. Root tidy-up procedure (standing instruction)
   229→   229→
   230→   230→The owner uploads files into the root of repositories without organizing them. When the root needs tidying, follow this procedure end to end, yourself, from start to finish.
   231→   231→
   232→   232→### CONFIGURATION (edit only if the owner wants something different)
   233→   233→
   234→   234→- **REPOS_TO_TIDY:** the current repository. If given access to several repositories, do them one by one, each on its own.
   235→   235→- **WORK_ON_BRANCH:** create a new branch called `chore/tidy-root` in each repo. Never work directly on `main` or `master`.
   236→   236→- **OPEN_PULL_REQUEST:** yes (if you can). If not, just push the branch.
   237→   237→- **FILES_ALLOWED_AT_ROOT_EXTRA:** none (add any file names here that the owner wants to keep at root).
   238→   238→- **DELETE_FILES:** never. Move or archive only.
   239→   239→- **CREATE_NEW_FOLDERS:** only when truly necessary (see STEP 3).
   240→   240→- **ASK_ME_QUESTIONS:** no. Decide on your own using the rules below. If something is truly risky, leave it where it is and list it in the final report.
   241→   241→
   242→   242→### YOUR JOB
   243→   243→
   244→   244→Tidy up the root of the repository so that only the important files remain there, and every other file lives in a sensible folder that fits that project's own structure. Important files such as AGENTS.md must be easy to see at the root.
   245→   245→
   246→   246→### STEP 1: UNDERSTAND THE PROJECT FIRST
   247→   247→
   248→   248→Before moving anything:
   249→   249→
   250→   250→- List every file and folder in the whole repository, not just the root.
   251→   251→- Read README, `package.json` / `pyproject.toml` / `requirements.txt` / `go.mod` / `wrangler.toml` / `composer.json` / any build or deploy config, and any CI files (`.github/workflows`).
   252→   252→- Work out what kind of project it is (WordPress plugin, Python tool, Cloudflare Worker, desktop app, web app, Go app, etc.).
   253→   253→- Write down (for yourself) a map of every folder that already exists and what it is used for. You will use this map in STEP 3.
   254→   254→
   255→   255→### STEP 2: WHAT MUST STAY AT ROOT
   256→   256→
   257→   257→Keep these at root (only the ones that exist):
   258→   258→
   259→   259→- AGENTS.md and any other agent rules file (per the READ THIS FIRST section, AGENTS.md is the only agent-instruction file — never create another)
   260→   260→- README, LICENSE, CHANGELOG, CONTRIBUTING, SECURITY
   261→   261→- `.gitignore`, `.gitattributes`, `.editorconfig`, `.env.example`
   262→   262→- Dependency and build files that tools require at root: `package.json`, `package-lock.json`, `pyproject.toml`, `requirements.txt`, `go.mod`, `go.sum`, `composer.json`, `Makefile`, `Dockerfile`, `docker-compose.yml`, `wrangler.toml`, vite/webpack/tsconfig/eslint/prettier configs, and the main plugin file of a WordPress plugin
   263→   263→- Hidden config folders: `.github`, `.vscode`, `.claude` and similar
   264→   264→- The main source folders (src, app, lib, etc.)
   265→   265→- Anything listed in FILES_ALLOWED_AT_ROOT_EXTRA
   266→   266→
   267→   267→AGENTS.md must be the most visible thing: make sure it sits at root and is not buried or duplicated. If there are several copies or variants, keep the newest one at root and move the others into the project's existing archive folder (or, if none exists, see STEP 3).
   268→   268→
   269→   269→### STEP 3: WHERE THINGS GO (REUSE FIRST, CREATE LAST)
   270→   270→
   271→   271→This is the most important rule for choosing folders:
   272→   272→
   273→   273→**RULE A. Use the project's existing structure first.** For every file that leaves the root, look at the folder map from STEP 1 and put the file into the existing folder that already serves that purpose, even if the folder name is different from what you would have chosen. Examples:
   274→   274→
   275→   275→- If specs and documents already live in a folder called `spec`, put new spec and document files there. Do NOT create `docs` or `documents-and-specs` next to it.
   276→   276→- If images already live in `img`, `images`, `static` or `public`, use that. Do NOT create `assets`.
   277→   277→- If scripts already live in `tools` or `bin`, use that. Do NOT create `scripts`.
   278→   278→- If there is already an `old`, `backup` or `archive` folder, use it. Do NOT create `docs/archive`.
   279→   279→
   280→   280→**RULE B. Never create overlapping or duplicate folders.** Before creating any folder, check if an existing folder, under any name, already covers the same kind of content. If one does, use it. Never end up with two folders that mean the same thing (for example `docs` and `documentation`, or `scripts` and `tools` doing the same job).
   281→   281→
   282→   282→**RULE C. Create a new folder only if all of these are true:**
   283→   283→1. No existing folder covers that kind of file.
   284→   284→2. There are enough files of that kind to justify a folder (a single stray file can go into the closest existing folder instead).
   285→   285→3. The new folder name follows the naming style the project already uses (lowercase or capitalized, singular or plural, etc.).
   286→   286→
   287→   287→**RULE D. Keep it flat.** Do not create sub-folders unless the files truly need them. One level is the default. Do not add nested folders such as `docs/archive/old` just for neatness.
   288→   288→
   289→   289→**RULE E. If no structure exists at all** (a brand-new messy repo), use the normal convention for that project type, and keep it as small as possible. Common choices: `docs`, `scripts`, `assets`, `data`, `tests`, `config`, `archive`. Create only the ones you actually need.
   290→   290→
   291→   291→**RULE F. When unsure where a file belongs**, put it in the closest existing folder, or the existing archive folder, and mention it in the report. Never leave a file at root just because you are unsure.
   292→   292→
   293→   293→### STEP 4: DO NOT BREAK ANYTHING
   294→   294→
   295→   295→This matters more than tidiness. For every file you move:
   296→   296→
   297→   297→- Use `git mv` so history is kept.
   298→   298→- Search the whole repo for references to that file (imports, require, includes, paths in scripts, README links, CI workflows, Dockerfile, config files, WordPress include/require paths) and update them so everything still works.
   299→   299→- Never move a file that a tool or platform requires at a fixed location (for example `wrangler.toml`, the WordPress main plugin file, workflow files, `package.json`). When in doubt, leave it.
   300→   300→- Never touch, print, or move secrets (`.env`, keys, tokens). If a secret is committed in the repo, do not copy it anywhere. Add it to the final report as a warning.
   301→   301→- Never delete anything.
   302→   302→- Never rewrite file contents except to fix paths after a move.
   303→   303→- Do not rename or reorganize folders that already exist. Only add files into them.
   304→   304→
   305→   305→### STEP 5: CHECK YOUR WORK
   306→   306→
   307→   307→After moving:
   308→   308→
   309→   309→- Run the project's build, tests, or at least a syntax/import check (for example: `npm run build`, `python -m py_compile`, `go build`, `php -l`).
   310→   310→- Check that no broken paths remain by searching for the old file names.
   311→   311→- Check that the root now contains only the allowed items from STEP 2.
   312→   312→- Check that you did not create any folder that overlaps with an existing one. If you did, merge it into the existing folder.
   313→   313→- If a check fails, fix it or undo that specific move.
   314→   314→
   315→   315→### STEP 6: COMMIT AND REPORT
   316→   316→
   317→   317→- Make small, clear commits (for example `chore: move loose specs into spec/`, `chore: move old backups into archive/`).
   318→   318→- Push the branch and open a pull request if possible.
   319→   319→- Finish with a short plain-language report (no technical jargon):
   320→   320→  1. What the root looked like before and after (two short lists)
   321→   321→  2. Where each moved file went and why (one line each)
   322→   322→  3. Any new folder you created and why none of the existing folders could be used (if you created none, say so)
   323→   323→  4. Any path references you updated
   324→   324→  5. Anything you left alone and why
   325→   325→  6. Any warnings (committed secrets, duplicate files, broken things you could not fix)
   326→   326→
   327→   327→Start when the owner asks for a tidy-up, and do not stop until every repository's root is clean and verified.
